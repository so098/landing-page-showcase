# 설계서 — 광고 기반 온라인 주문 매출화 + 하이브리드 배포(AWS)

- 작성일: 2026-06-04
- 상태: 설계 (사용자 리뷰 대기)
- 종류: 프로그램 설계서 (여러 하위 시스템을 단계로 분해 — 1단계만 이후 상세 구현 스펙으로 전개)

## 1. 배경과 목표

멜스튜디오를 **실제 매출이 나는 서비스**로 운영한다. 1차 매출 모델은 **광고 유입 → 온라인 주문 접수 → 결제**다. 동시에, 사업이 불확실할 수 있으므로 이 작업물을 **프론트엔드 이직 포트폴리오**로도 남긴다.

두 목표는 충돌하지 않고 **한 작업으로 합쳐진다**:

- 광고는 클릭당 비용이므로 **사이트 속도·전환율이 곧 ROI**다 → "광고 유입→주문 전환 퍼널을 측정하고 개선"하게 된다.
- 그 측정/개선 활동이 이 레포의 테마 **"측정하고 개선했어요"** 와 정확히 같다. 합성 Lighthouse 수치보다 **실제 광고 전환 퍼널 개선** 이 면접에서 더 강하다.
- 결제·주문 실연동은 "목 데이터 토이"가 아닌 **진짜 제품**이라는 증거 + "실무 연동 경험"이 된다.

### 핵심 전제 (전략의 축)

> **매출의 실제 잠금장치는 배포가 아니라 결제다.** 현재 로그인/주문/결제는 전부 목(mock)이다(`orderStorage`=sessionStorage). 결제가 안 되는 사이트에 광고를 돌리면 광고비만 태운다. 따라서 **광고는 결제·주문이 진짜로 동작한 뒤** 켠다.

## 2. 목표 아키텍처 — 하이브리드

스택을 쪼개, 각 부분을 가장 적합한 곳에 둔다. "전부 AWS"의 시간·성능 비용과 "전부 매니지드"의 학습가치 부족을 동시에 피한다.

```
[사용자/광고 유입]
        │  HTTPS
        ▼
┌──────────────────────┐        ┌───────────────────────────┐
│  web (Next.js 16)    │        │  api (Express + Socket.IO) │
│  Vercel              │ ─────▶ │  AWS (컨테이너)            │
│  - RSC/ISR/SSR       │  REST  │  - 주문/결제/리뷰/채팅     │
│  - 광고 랜딩·전환 최적│  /WS   │  - 공개 HTTPS 엔드포인트   │
└──────────────────────┘        └─────────────┬─────────────┘
        │                                      │
   Vercel Analytics                            ▼
   (전환 측정)                        ┌───────────────────┐
                                      │ AWS RDS (Postgres)│
                                      │  - 주문/결제/리뷰  │
                                      └───────────────────┘
        결제 웹훅: PortOne ──────▶ api 공개 URL (서버 금액검증/상태확정)
```

| 부분 | 위치 | 이유 |
|---|---|---|
| **web (Next.js)** | **Vercel** | Next는 Vercel제. 광고 전환에 직결되는 성능 최상 + 운영 0 + 취미요금 무료. ISR/Server Actions가 마찰 없이 동작 |
| **api (Express+Socket.IO)** | **AWS 컨테이너** | ECS·RDS·VPC·IaC 등 **진짜 AWS 경험이 자연스럽게 사는 자리**. WebSocket(Socket.IO) 정상 동작. 결제 웹훅을 받을 공개 HTTPS |
| **DB** | **AWS RDS (Postgres)** | 첫 12개월 프리티어. 실데이터 + AWS 생태계 학습. api와 같은 VPC 내 사설 서브넷 |
| **시크릿** | **AWS SSM Parameter Store / Secrets Manager** | `DATABASE_URL`, PortOne 키 등. 코드/이미지에 비밀 미포함 |
| **이미지 레지스트리** | **AWS ECR** | api 컨테이너 이미지 |

**비용 함정 회피 원칙**: NAT Gateway(월 ~$32)·다중 ALB 같은 고정비를 의도적으로 피한다. api는 아웃바운드가 필요하면 퍼블릭 서브넷+보안그룹 또는 VPC 엔드포인트로 NAT를 회피한다.

## 3. 단계 분해 (의존성 기반 순서)

각 단계는 **스펙 → 구현(테스트 포함) → 측정 → 사람 확인** 사이클을 따른다. 단계 사이의 순서는 기술적 의존성으로 결정한다.

### Phase 1 — 하이브리드 배포 + IaC + CD  ★ 먼저
- **왜 먼저**: 결제 웹훅/서버검증을 안정적으로 받으려면 **공개 HTTPS api가 선행**되어야 한다. 또한 실배포 환경이 있어야 이후 결제를 실조건에서 검증한다. AWS 학습·CI/CD 가치도 큼.
- web → Vercel 연결(프로젝트 import, 환경변수, 커스텀 도메인/SSL)
- api → AWS 컨테이너화(Dockerfile) → ECR → **ECS/Fargate 서비스 + ALB**(WebSocket 지원, 헬스체크/롤링배포)
- 네트워크 → VPC + 퍼블릭/사설 서브넷, 보안그룹. NAT 회피(Fargate 퍼블릭 서브넷+퍼블릭IP 또는 ECR/SSM VPC 엔드포인트)
- DB → RDS Postgres(프리티어, 사설 서브넷), 마이그레이션 적용
- 시크릿 → SSM/Secrets Manager, api가 런타임에 주입받음
- **IaC**: 인프라 전체를 **Terraform**으로 정의 — 재현/파괴 가능, 빌링 알람 포함
- **CD**: GitHub Actions에서 기존 CI 통과 후 → 이미지 빌드→ECR 푸시→서비스 갱신, web은 Vercel 자동 배포
- 환경변수 정리: `NEXT_PUBLIC_API_URL`(Vercel→api 공개URL), `DATABASE_URL`, `WEB_ORIGIN`(CORS/Socket.IO)
- Socket.IO 배포환경 WebSocket 동작 확인
- **테스트**: 배포 후 라이브 URL 대상 Playwright smoke 1개(핵심 흐름) + CD에서 기존 전체 테스트 자동 실행
- **사람 확인**: 폰에서 라이브 URL 접속, 쇼케이스/채팅 동작, 결제 웹훅용 공개 URL 확보

### Phase 2 — 주문 + 결제 실연동 (PortOne)  ★ 매출 잠금 해제
- **선행(사람)**: PortOne 가입 + 테스트 채널 키 발급
- api: `Order`/`Payment` 모델 + `POST /api/orders` + `POST /api/payments/verify`(**서버 금액 검증** — 위변조 거부) + 결제 웹훅 수신
- web: 주문서 제출(현재 목 → 실제) → 결제창 → 성공 시 생성 진행 / 실패·취소 처리
- 주문 상태머신: 시도/성공/실패/취소 → 마이페이지 결제내역 실데이터화
- **인증은 선택**: v1은 비로그인 주문(이메일/연락처 입력)으로도 매출 가능. 카카오 OAuth(로드맵 4순위)는 "주문 이력/마이페이지 개인화"가 필요해지면 그때. → 광고-주문 최단 경로를 막지 않도록 **auth는 후순위**
- 후속: 주문 접수 시 메일 전송(Resend → szerohan@gmail.com)
- **테스트**: api 금액검증/위변조 거부, 결제 상태별 UI 분기 RTL, 주문→테스트결제→완료 Playwright
- **사람 확인**: 테스트 카드 결제 → 성공 → 마이페이지 PAID 확인 → 취소 시 진행 안 됨

### Phase 3 — 전환 분석 (광고→주문 퍼널)
- 퍼널 정의: 광고 유입 → 주문서 진입 → 주문 제출 → 결제 성공
- Vercel Analytics(또는 GA4) + 핵심 단계 이벤트. 이탈 지점 가시화
- **매출·포폴 동시**: 광고비 ROI 최적화 = "측정→병목발견→개선" 서사
- **테스트**: 이벤트 발화 단위 테스트(핵심 전환 포인트)
- **사람 확인**: 대시보드에서 단계별 전환/이탈 확인

### Phase 4 — 광고 런칭 + 측정/개선 루프
- 소액 예산으로 광고 시작(채널은 사업 판단)
- 전환 데이터 기반 A/B·랜딩 개선 반복
- README/포폴에 "실광고 전환 퍼널 측정·개선" 케이스로 기록

### 곁다리(병행 가능, 계정 불필요)
- **next/font 전환**: perf 측정에서 도출된 "진짜 병목=렌더 블로킹 폰트" 개선. 광고 전환(LCP)에 직접 이득 + 측정 서사. Phase 1~2 사이 끼우기 좋음.

## 4. 핵심 설계 결정과 트레이드오프

| 결정 | 선택지 | 권고 | 비고 |
|---|---|---|---|
| api 실행 환경 | App Runner / **ECS/Fargate+ALB** | **확정: ECS/Fargate + ALB** | "AWS 경험이 목표" → VPC·서브넷·ALB·타깃그룹을 직접 구성하는 진짜 인프라. ALB 고정비(월 ~$18)·설정량 감수 |
| IaC 도구 | **Terraform** / AWS CDK | **확정: Terraform** | 업계 표준·면접 범용성·AWS 외 클라우드에도 전이되는 지식. HCL 학습 |
| 인증 | v1 비로그인 주문 / 카카오 OAuth | **v1 비로그인** | 광고-주문 최단 경로 우선. OAuth는 개인화 필요 시 |
| web 호스팅 | Vercel / AWS(Amplify) | **Vercel** | 광고 ROI=성능 우선. AWS 깊이는 api/DB로 충분히 확보 |

## 5. 비용 개략 (대략 — 배포 시 실측/확인)

- **web(Vercel)**: 취미요금 무료(상업적 트래픽이 커지면 Pro 검토)
- **api**: Fargate 소형 태스크(상시 구동, Socket.IO) + ALB 고정비(월 ~$18)
- **DB(RDS)**: 첫 12개월 프리티어(t-class micro), 이후 소액
- **회피**: NAT Gateway·다중 ALB 등 고정비 함정
- 대략 **월 $25~45 바닥**(ALB ~$18 + Fargate 소형 + RDS, 첫 해는 RDS 프리티어로 더 낮음). 정확치는 Phase 1에서 실측.

## 6. 리스크와 완화

- **결제 전 광고 → 광고비 낭비**: 순서를 강제(결제 후 광고). Phase 4는 Phase 2 완료에 의존.
- **AWS 비용 폭증(NAT/ALB/유휴)**: 고정비 함정 회피 설계 + 빌링 알람 + IaC로 손쉬운 파괴/재생성.
- **Next.js를 AWS에 올리는 마찰**: web을 Vercel로 둬 원천 회피.
- **결제 보안(금액 위변조)**: 서버 금액 검증 필수 + 웹훅 서명 검증.
- **시크릿 노출**: 이미지/코드에 비밀 미포함, SSM/Secrets Manager 런타임 주입.
- **CORS/WebSocket 출처**: `WEB_ORIGIN`로 Vercel 도메인 허용, Socket.IO 핸드셰이크 확인.

## 7. 테스트/검증 전략

원칙(레포 공통): 각 단계는 해당 기능 테스트를 포함한다.
- 단위/컴포넌트: Vitest + RTL (web), Vitest + supertest (api, 실DB)
- 흐름: Playwright E2E (주문→결제, 라이브 smoke)
- 인프라: IaC plan 리뷰 + 배포 후 헬스체크/smoke
- 결제: 금액 위변조 거부, 상태머신 분기

## 8. 확정된 결정 / 남은 세부 (Phase 1 계획에서)

**확정**: api=ECS/Fargate+ALB · IaC=Terraform · web=Vercel · DB=RDS · v1 비로그인 주문

**Phase 1 계획에서 정할 세부**:
1. RDS 인스턴스 클래스/가용영역(단일 AZ로 시작)
2. NAT 회피 방식(퍼블릭 서브넷+퍼블릭IP vs VPC 엔드포인트)
3. 커스텀 도메인 보유 여부 / 발급 계획
4. Terraform state 백엔드(S3+DynamoDB lock vs 로컬)
